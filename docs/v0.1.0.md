## Benchmarks

Run with `mix bench` (Benchee, `time: 1s` / `warmup: 0.5s` per scenario). Each
suite writes a diff-able CSV and an HTML report to `bench/results/` (gitignored).
See `benchmarks.md` for the suite design and how to re-run.

### Schedule — `:serial` vs `:parallel`

`:serial` vs `:parallel` across rule **scale** (50 / 200 / 1000) and rule
**width** (`narrow` = 2 conditions, `wide` = 20 conditions per rule).

| Scale | Width | Schedule | ops/s | avg | p99 |
| ---: | --- | --- | ---: | ---: | ---: |
| 50 | narrow | serial | 3,614 | 0.277 ms | 0.488 ms |
| 50 | narrow | parallel | 1,003 | 0.997 ms | 2.095 ms |
| 50 | wide | serial | 373 | 2.677 ms | 4.237 ms |
| 50 | wide | parallel | 229 | 4.359 ms | 7.746 ms |
| 200 | narrow | serial | 806 | 1.240 ms | 2.934 ms |
| 200 | narrow | parallel | 314 | 3.184 ms | 5.225 ms |
| 200 | wide | serial | 99 | 10.077 ms | 15.206 ms |
| 200 | wide | parallel | 69 | 14.456 ms | 20.306 ms |
| 1000 | narrow | serial | 183 | 5.476 ms | 9.398 ms |
| 1000 | narrow | parallel | 63 | 15.911 ms | 38.841 ms |
| 1000 | wide | serial | 17 | 59.727 ms | 78.762 ms |
| 1000 | wide | parallel | 13 | 79.014 ms | 117.986 ms |

On this machine, `:parallel` was **slower than `:serial` in every scenario**.
The rules here are cheap, so the per-run shared-almanac GenServer that every fact
lookup round-trips through dominates. `:parallel` only wins when rules are wide
*and* expensive enough that the overlap saves more than the round-trips cost — the
suite exists to make that trade-off visible on *your* machine, not to crown a
winner. Default to `:serial`.

### Store — `:pure` / `:genserver` / `:ets`

The three store backends at a fixed workload (200 rules, 2 conditions each).

| Store | ops/s | avg | p99 |
| --- | ---: | ---: | ---: |
| `:pure` | 806 | 1.240 ms | 2.281 ms |
| `:genserver` | 749 | 1.335 ms | 1.955 ms |
| `:ets` | 613 | 1.632 ms | 2.911 ms |

`:pure` (a plain struct) is the fastest; `:ets` is the slowest of the three (~1.3x
at this scale). The store affects how rules/facts are *held*, not how they are
evaluated — at 200 rules the difference is small. Reach for `:genserver`/`:ets`
when you need a supervised or very large shared store, not for raw speed.

### Fact cost — constant vs dynamic

Fact computation cost crossed with schedule (scale 100, ~20,000 ops per dynamic
fact reference). `dynamic` facts use `cache: false`, so they are recomputed on
*every* rule reference.

| Schedule | Fact | ops/s | avg | p99 |
| --- | --- | ---: | ---: | ---: |
| serial | constant | 3,147 | 0.318 ms | 0.575 ms |
| parallel | constant | 856 | 1.169 ms | 1.961 ms |
| parallel | dynamic | 437 | 2.289 ms | 3.810 ms |
| serial | dynamic | 83 | 12.107 ms | 14.112 ms |

This is the opposite shape of the schedule suite: here a **single expensive dynamic
fact** dominates the cost. `:parallel` overlaps that recomputation across worker
processes, so `parallel/dynamic` (2.29 ms) is ~5.3x faster than `serial/dynamic`
(12.11 ms). The gap between those two rows is exactly what `:parallel` is for —
hiding a costly, independent, repeatedly-read fact. A cached dynamic fact (the
default) avoids most of this cost without any parallelism.
