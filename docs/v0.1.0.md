## Benchmarks

Run with `mix bench` (Benchee, `time: 1s` / `warmup: 0.5s` per scenario). Each
suite writes a diff-able CSV and an HTML report to `bench/results/` (gitignored).
Six suites ship — `schedule`, `store`, `fact`, `slowfacts`, `engines`, and `matrix` —
covering schedule, store backend, fact cost, short-circuiting, and the full
configuration matrix (store × schedule × short-circuit × fact speed × caching). See
`benchmarks.md` for the suite design and how to re-run.

### Schedule — `:serial` vs `:parallel`

`:serial` vs `:parallel` across rule **scale** (50 / 200 / 1000) and rule
**width** (`narrow` = 2 conditions, `wide` = 20 conditions per rule).

| Scale | Width | Schedule | ops/s | avg | p99 |
| ---: | --- | --- | ---: | ---: | ---: |
| 50 | narrow | serial | 3,614 | 0.277 ms | 0.488 ms |
| 50 | narrow | parallel | 1,003 | 0.997 ms | 2.095 ms |
| 50 | wide | serial | 373 | 2.677 ms | 4.237 ms |
| 50 | wide | parallel | 229 | 4.359 ms | 7.746 ms |
| 200 | narrow | serial | 806 | 1.240 ms | 2.934 ms |
| 200 | narrow | parallel | 314 | 3.184 ms | 5.225 ms |
| 200 | wide | serial | 99 | 10.077 ms | 15.206 ms |
| 200 | wide | parallel | 69 | 14.456 ms | 20.306 ms |
| 1000 | narrow | serial | 183 | 5.476 ms | 9.398 ms |
| 1000 | narrow | parallel | 63 | 15.911 ms | 38.841 ms |
| 1000 | wide | serial | 17 | 59.727 ms | 78.762 ms |
| 1000 | wide | parallel | 13 | 79.014 ms | 117.986 ms |

On this machine, `:parallel` was **slower than `:serial` in every scenario**.
The rules here are cheap, so the per-run shared-almanac GenServer that every fact
lookup round-trips through dominates. `:parallel` only wins when rules are wide
*and* expensive enough that the overlap saves more than the round-trips cost — the
suite exists to make that trade-off visible on *your* machine, not to crown a
winner. Default to `:serial`.

### Store — `:pure` / `:genserver` / `:ets`

The three store backends at a fixed workload (200 rules, 2 conditions each).

| Store | ops/s | avg | p99 |
| --- | ---: | ---: | ---: |
| `:pure` | 806 | 1.240 ms | 2.281 ms |
| `:genserver` | 749 | 1.335 ms | 1.955 ms |
| `:ets` | 613 | 1.632 ms | 2.911 ms |

`:pure` (a plain struct) is the fastest; `:ets` is the slowest of the three (~1.3x
at this scale). The store affects how rules/facts are *held*, not how they are
evaluated — at 200 rules the difference is small. Reach for `:genserver`/`:ets`
when you need a supervised or very large shared store, not for raw speed.

### Fact cost — constant vs dynamic

Fact computation cost crossed with schedule (scale 100, ~20,000 ops per dynamic
fact reference). `dynamic` facts use `cache: false`, so they are recomputed on
*every* rule reference.

| Schedule | Fact | ops/s | avg | p99 |
| --- | --- | ---: | ---: | ---: |
| serial | constant | 3,147 | 0.318 ms | 0.575 ms |
| parallel | constant | 856 | 1.169 ms | 1.961 ms |
| parallel | dynamic | 437 | 2.289 ms | 3.810 ms |
| serial | dynamic | 83 | 12.107 ms | 14.112 ms |

This is the opposite shape of the schedule suite: here a **single expensive dynamic
fact** dominates the cost. `:parallel` overlaps that recomputation across worker
processes, so `parallel/dynamic` (2.29 ms) is ~5.3x faster than `serial/dynamic`
(12.11 ms). The gap between those two rows is exactly what `:parallel` is for —
hiding a costly, independent, repeatedly-read fact. A cached dynamic fact (the
default) avoids most of this cost without any parallelism.

### Slow facts — where `:parallel` wins

The realistic `Data` dataset (structured `transaction`/`customer` facts read with
JSONPath, a mix of operators, `all`/`any`, a named `high_risk` condition) with its
`fraud_score` fact made expensive and `cache: false`, so it is recomputed on every
rule reference. `:serial` pays that cost straight-line; `:parallel` overlaps it.

| scale | serial avg | parallel avg | parallel vs serial |
| ---: | ---: | ---: | ---: |
| 100 | 37.9 ms | 6.7 ms | ~5.6x faster |
| 500 | 185.9 ms | 24.2 ms | ~7.7x faster |
| 2000 | 772.6 ms | 84.3 ms | ~9.2x faster |

With **slow facts, `:parallel` wins**, and the speedup grows with scale (more
independent work to overlap). The `fast` baseline in the same suite inverts this:
with cheap facts `:parallel` is *slower* (overhead dominates) — so the `schedule`
and `slowfacts` suites together show the full crossover.

### Engine matrix — short-circuit × schedule

`strict` controls short-circuiting of `all`/`any`: `strict: false` (the default)
stops at a deciding condition and skips the rest; `strict: true` evaluates every
condition (for a complete report). The `Data.engines_engine/2` dataset gives each
rule a cheap failing head (evaluated first) plus an expensive tail of 3 slow
`fraud_score` conditions, so short-circuit skips the tail.

| config | scale 100 | scale 500 | scale 2000 |
| --- | ---: | ---: | ---: |
| short-circuit, serial | 0.74 ms | 3.52 ms | 16.44 ms |
| short-circuit, parallel | 1.65 ms | 7.89 ms | 32.81 ms |
| strict, serial | 105.6 ms | 530.4 ms | 2122.6 ms |
| strict, parallel | 11.1 ms | 45.6 ms | 189.3 ms |

Three advantages of the engines fall out of the matrix:

- **Short-circuit is the biggest lever** — skipping the tail is ~130-140x faster
  than `strict` at the same scale. Use it whenever you do not need every
  condition's result.
- **Under short-circuit, `:serial` beats `:parallel`** (~2x) — once the tail is
  skipped there is little independent work to overlap, so the parallel machinery's
  overhead wins out.
- **Under `strict`, `:parallel` wins** (~10x) — it *must* evaluate the expensive
  tail and overlaps that work across workers. This is the parallel engine's
  advantage: complete evaluation of expensive rules.

### Matrix — store × schedule × short-circuit × fact cost × caching

Where the other suites isolate one axis, this crosses them on a **deep,
priority-varied, nested** rule (a cheap head that decides the `all` early, plus a
nested `any` group and leaf conditions at distinct priorities), so the *interactions*
show. Scale 200.

**A — storage × run mode** (slow, uncached facts):

| store | short-circuit | schedule | avg |
| --- | --- | --- | ---: |
| `:pure` | on | serial | 1.60 ms |
| `:pure` | on | parallel | 5.16 ms |
| `:pure` | off | serial | 371.9 ms |
| `:pure` | off | parallel | 31.3 ms |
| `:genserver` | on | serial | 2.19 ms |
| `:genserver` | on | parallel | 5.48 ms |
| `:genserver` | off | serial | 352.7 ms |
| `:genserver` | off | parallel | 30.7 ms |
| `:ets` | on | serial | 1.95 ms |
| `:ets` | on | parallel | 8.22 ms |
| `:ets` | off | serial | 368.3 ms |
| `:ets` | off | parallel | 32.1 ms |

**B — fact cost × caching** (pure store):

| speed | cache | short-circuit | schedule | avg |
| --- | --- | --- | --- | ---: |
| fast | cached | on | serial | 1.57 ms |
| fast | cached | off | serial | 4.09 ms |
| fast | cached | off | parallel | 5.05 ms |
| slow | cached | on | serial | 1.49 ms |
| slow | cached | off | serial | 4.80 ms |
| slow | cached | off | parallel | 5.35 ms |
| slow | uncached | off | serial | 456.0 ms |
| slow | uncached | off | parallel | 30.8 ms |

Across the 28 combinations, five effects stand out:

- **Short-circuit is the dominant lever** — skipping the deep tail is ~300x at the
  extreme (456 ms → 1.5 ms).
- **Caching only matters for an expensive fact that is actually evaluated** —
  `strict`+`slow`+`serial`: cached 4.8 ms vs uncached 456 ms (~95x).
- **Fact speed is irrelevant under short-circuit** — the tail is never evaluated.
- **`:serial` wins under short-circuit; `:parallel` rescues `strict`+`slow`+`uncached`**
  (456 ms → 31 ms, ~15x) by overlapping the recomputation.
- **`:pure` is the fastest store; `:parallel` hides the store difference** (all
  ~31-32 ms at `strict`).

> The extreme cells take hundreds of ms per run, so they carry only a few samples —
> order-of-magnitude, not precise. Re-run `mix bench matrix` on your own machine.
